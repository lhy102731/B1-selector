## 4. Closed P0 contracts

### 4.1 Phases and side effects

`Phase` remains exactly `P0` through `P8`. `SideEffect` becomes a closed enum with exactly:

```text
READ
WRITE_STAGING
WRITE_CONTROL_PLANE
RUN_RESEARCH
WRITE_KBASE
OPEN_HOLDOUT
GIT_MUTATION
WRITE_PRODUCTION_DATA
WRITE_PRODUCTION_CONFIG
DELETE_PATH
NETWORK_EGRESS
START_SUBPROCESS
START_BACKGROUND_WORK
SEND_NOTIFICATION
EXPOSE_SERVICE
```

P0 runtime grants permit only `READ` and `WRITE_CONTROL_PLANE`. Adding an enum member never grants it. Unknown or dynamically supplied effects fail closed.

### 4.2 Authorization chain

The only accepted chain is:

```text
pre-provisioned AuthorizationEnvelope
  -> PhaseGrant
  -> one-effect TaskTicket
  -> SideEffectLease
  -> terminal TicketSnapshot
```

Required public operations:

```python
claim_phase(authorization_ref, bearer_secret, actor, identity_binding) -> PhaseGrant
issue_task_ticket(phase_grant, entry_id, effect, resource_scope, idempotency_key) -> TaskTicket
begin_side_effect(task_ticket, expected_entry_id, expected_effect, expected_resource) -> SideEffectLease
finish_side_effect(lease, outcome, evidence_ref) -> TicketSnapshot
record_gate(phase_grant, verified_gate_report) -> GateSnapshot
```

Rules:

- The production library exposes no method that provisions an authorization envelope.
- The database path is fixed at `research_state/control_plane/p0/control_plane.sqlite3`; a caller-supplied path cannot create authority.
- A missing database, missing envelope, unknown schema, public hashes alone, or an arbitrary dataclass fails closed.
- `authorization_ref` is an opaque lookup key. The random bearer secret is the credential; only its SHA-256 is stored.
- An envelope binds exactly one phase, actor ID/type, invocation ID, plan hash, scope hash, policy hash, and secret hash. Claim is single-use.
- A PASS gate is a prerequisite fact only. It does not provision or mint the next phase.
- A FAIL gate closes the attempt. Retrying P0 requires a newly provisioned authorization reference and a fresh user command.
- A task ticket binds one entry, one effect, one canonical resource scope, the full actor/invocation, all approved hashes, and one idempotency key.
- Same idempotency key plus identical semantics returns the existing ticket. The same key with different semantics fails.
- The database stores only secret hashes. Frozen dataclasses are projections and cannot authorize an action on their own.
- `issue_phase_token`, direct `AuthorizationGrant`, and raw-grant `assert_side_effect` remain only as fail-closed legacy shims and are not exported as authority.

### 4.3 SQLite schema and crash semantics

Schema version is `2` and uses these append-safe tables:

```text
authorizations: PENDING -> CLAIMED | REVOKED
phase_grants: ACTIVE -> PASSED | FAILED | REVOKED
task_tickets: ISSUED -> IN_PROGRESS -> SUCCEEDED | FAILED | IN_DOUBT
side_effect_events: append-only
phase_gates: immutable row per grant
control_plane_meta: schema and approved identity binding
```

The old `phase_tokens` and old `phase_gates` remain read-only `LEGACY_UNTRUSTED` audit evidence. They are never upgraded. Migration and every state transition use `BEGIN IMMEDIATE` plus conditional writes. Unknown future schema versions fail closed.

P0 has no automatic replay or reconciliation. If an effect starts and completion cannot be proven in the same process, its ticket becomes `IN_DOUBT`. An open or `IN_DOUBT` ticket prevents a PASS gate. Resolution requires a later separately authorized design; file age or timeout never authorizes replay.

### 4.4 Canonical resource containment

Identity canonicalization and access control are separate. Access checks must:

- resolve against an approved root and compare normalized Windows paths case-insensitively;
- reject `..`, drive-relative paths, unapproved UNC paths, `\\?\` aliases, alternate data streams, and paths escaping through a symlink or junction;
- inspect existing parent reparse points before an effect;
- bind the resolved target into the ticket and repeat containment at `begin_side_effect`;
- never infer safety from string prefix comparison.

## 5. Entry inventory and policy

### 5.1 Scan surface

Inventory covers root `*.py`, `*.bat`, `*.ps1`, `*.sh` and project code beneath `apps/`, `tools/`, `research_automation/`, `ag2_research/`, `research/`, `l2/`, `strategy/`, `utils/`, and `tests/`. It also records dynamic import seams and external scheduler records.

The scanner does not follow symlinks/junctions/reparse points and excludes these directory names or roots deterministically:

```text
.git .agents .claude .codex_pydeps .venv venv node_modules
__pycache__ .pytest_cache .idea .vscode
data artifacts archive tmp research_state research_automation/_output
dist build *.egg-info
```

Excluding root `data/` must not exclude `tools/data/`. Raw data and generated outputs are never recursively listed or hashed.

### 5.2 Entry policy

`entry_policy.json` is reviewed policy, not scanner output. Each record contains:

```text
entry_id, path, kind, callable_name, content_sha256,
actor_type, disposition, trust_state,
declared_side_effects, declared_phase, resource_roots, source
```

Closed dispositions are:

```text
CONTROLLED_RESEARCH
LEGACY_UNAUDITED
PRODUCTION_DAILY
ADMIN_ONLY
TEST_ONLY
DENIED_WEB
```

An entry ID, path, callable, content hash, phase, effect, disposition, or resource-root mismatch denies trusted execution. Scanner output cannot approve itself.

Historical research scripts, maintenance CLIs, and their existing outputs remain usable only as non-authoritative evidence. Unless created by the new controller they derive:

```json
{
  "controller_created": false,
  "trust_state": "legacy_unaudited",
  "promotion_eligible": false
}
```

P0 does not implement a Ledger; it establishes the provenance boundary future phases must enforce.

## 6. Gate report

`p0_gate.py` computes the verdict. A caller cannot submit `PASS`. The canonical JSON schema requires:

```text
schema_version
phase
plan_hash
scope_hash
policy_hash
authorization_ref
task_reports
entry_inventory_ref
entry_inventory_sha256
entry_policy_ref
entry_policy_sha256
baseline_ref
test_runs
side_effect_summary
external_scheduler_inventory
changed_files
unexpected_changes
unresolved_risks
gate_status
auto_advance
self_hash
```

`self_hash` is SHA-256 over canonical JSON with only `self_hash` omitted. A PASS requires:

- exact plan/scope/policy binding;
- every P0 task report terminal and successful;
- complete inventory and exact entry-policy match;
- no open/failed/`IN_DOUBT` P0 ticket;
- all required RED evidence, GREEN evidence, targeted tests, fault tests, and full regression passing;
- no unexpected change outside the scope lock relative to the P0 implementation baseline;
- no research, KBase, Holdout, Git, production-data/config, network, subprocess, background-work, notification, or service-exposure ticket issued by P0;
- `auto_advance=false` and no P1 authorization.

The Markdown report is supplementary. Only validated `gate_report.json` can close P0.

## 7. Parallel development protocol

External development is mandatory and runs in two parallel proposal batches using this exact roster:

```text
volcengine: glm51, doubao, kimi_hs, minimax_hs
deepseek_official: deepseekv4
```

Batch A covers contracts, authorization, inventory, import safety, and gate design. Batch B covers execution sinks, authority writes, loops, web entries, and integration tests. Each profile receives a non-overlapping lane and returns a patch/test proposal; external models never directly mutate the workspace. No failed profile is silently replaced. Provider/model/status/token usage is recorded. If a quota is exhausted, the main controller implements that lane.

The main controller owns scope, applies/rejects proposals, and reviews every changed line. Internal implementers may edit only non-overlapping files. Every task has two ordered reviews: specification compliance first, then code quality. No task advances with an open review finding.

## 8. TDD execution rule

Every behavior is a vertical tracer bullet:

```text
write one public-behavior test
-> run and capture the expected RED failure
-> add the minimum implementation
-> run and capture GREEN
-> refactor only while GREEN
-> rerun the task module
```

Tests cannot be bulk-written ahead of implementation. Tests use temporary directories, fake clocks/processes, and local fixtures; they do not open a socket, call an LLM, invoke a protected research subprocess sink, modify production data, or execute research. The import-SLO test may launch only a fixed `python -B -c "import research_automation.control_plane"` child process to obtain an isolated cold-import measurement; it cannot execute any project workflow.

## 11. Exit conditions

P0 passes only when the canonical gate validator emits `gate_status=PASS`, its self-hash verifies, every test is green, every expected entry is represented, every dangerous sink fails before effects without a ticket, the cold-start SLO passes, no scope drift exists, and external reviews have no unresolved critical finding.

After PASS:

```text
AUTO_ADVANCE=false
AUTHORIZATION_CONSUMED=true
P1_AUTHORIZED=false
CAMPAIGN_NOT_AUTHORIZED=true
FINAL_EVAL_NOT_AUTHORIZED=true
```

The controller stops and waits. No Git operation occurs without a separate explicit command.

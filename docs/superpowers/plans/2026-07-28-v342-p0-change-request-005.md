# P0-CR-005: Freeze the repo-owned THSDK runtime surface

Status: `AWAITING_OPERATOR_APPROVAL`
Prepared: 2026-07-28
Supplements: approved `P0-CR-004`

## Why this is a major integrity issue

After the exact approval of `P0-CR-004`, the required independent review traced the new production data path through `utils/ths_yuanhang_bridge.py`.

That module can rebuild and then execute the repo-owned file:

```text
tools/ths_yuanhang_bridge/YuanhangBridge.dll
```

The current T7 scanner only inventories `.py`, `.bat`, `.ps1`, and `.sh`. It sees `build.ps1`, but it does not see the C# source, the resulting DLL, its runtime configuration, or the workspace XML files. A T7/T8 PASS could therefore leave actual production-executed bytes outside the freeze.

This is an execution-identity hole, not a data-quality improvement or a request to redesign the THSDK migration. P0 must stop before T7 until the exact repo-owned runtime surface is bound.

## Reproduced evidence

The public `EntryInventory.scan()` interface currently reports:

- `tools/ths_yuanhang_bridge/build.ps1`: present, but `ADMIN_ONLY`;
- `tools/ths_yuanhang_bridge/YuanhangBridge.cs`: absent;
- `tools/ths_yuanhang_bridge/YuanhangBridge.dll`: absent;
- `tools/ths_yuanhang_bridge/YuanhangBridge.runtimeconfig.json`: absent;
- `tools/ths_yuanhang_bridge/workspace/datacenter.xml`: absent;
- `tools/ths_yuanhang_bridge/workspace/DNSTest.xml`: absent.

The same review found that the current `daily_run.py` production chain is classified using the pre-THSDK path list. Its direct or bounded indirect daily children are currently misclassified as `ADMIN_ONLY` or `LEGACY_UNAUDITED`.

The Windows scheduler still points to `run_select.bat`, last ran at `2026-07-27T20:00:01+08:00`, and reports result `0`. Repository data/output timestamps between approximately 09:03 and 09:09 on 2026-07-28 cannot be attributed to that scheduler invocation. No matching process was running at review time. Those writes must remain `UNKNOWN_EXTERNAL_CONCURRENT_CHANGE`, never P0 or scheduler evidence.

# P0-CR-002: Replace V3.4.1-P0R1 with V3.4.2-P0R2

Status: `APPROVED_BY_OPERATOR_NATURAL_LANGUAGE_INSTRUCTION`  
Effective date: 2026-07-26

## Reason

P0R1 exposed structural conflicts after implementation began:

- its T1 and T2 reports use divergent schemas and status fields;
- T2 finished `BLOCKED_BY_PLAN_REVISION`;
- its 368-entry inventory and source entry policy were captured before later planned P0 code changes, so they cannot be final authority;
- its authorization is already claimed and cannot bind revised plan/scope/policy identities;
- extending the original design would duplicate state machines, queues, patch engines, context assembly, result adapters, configuration, cache identity, and token ledgers;
- using one physical control-plane store for both authority and operational facts makes trust ownership ambiguous.

## Approved changes

1. Version becomes `V3.4.2-P0R2`.
2. AuthorityStore and OperationalJournal use different SQLite files with a shared transaction implementation.
3. Authority outbox provides idempotent operational mirroring without a cross-store transaction.
4. TaskReport converges on `control_plane.task_report.v2`; legacy reports are immutable provisional evidence with explicit adoption reports.
5. One generic gate engine serves P0-P8.
6. Final entry inventory and reviewed policy are produced only after code freeze.
7. P0 trusted bootstrap/broker/store/gate code becomes sealed after P0 PASS.
8. Legacy TaskQueue/autorun/STOP/status and CapitalTracker authority are quarantined behind adapters.
9. Existing KBase publication, lineage, cache formats, isolated workspace, and standard/mature libraries are reused.
10. Token usage keeps `REPORTED`, `ESTIMATED`, or `UNKNOWN`; unknown is null and budget-safe.
11. One Git commit is created for every completed, verified small implementation stage, with exact-file staging.

## Evidence retained, not promoted

The following P0R1 assets remain byte-immutable and are referenced by hash:

- claimed implementation authorization;
- T1 contract/authority task report;
- T2 inventory/import task report;
- initial entry inventory and scheduler inventory;
- provisional source entry policy;
- P0R1 plan/scope/baseline/freeze manifests.

None independently satisfies a P0R2 task or gate.

The P0R2 receipt records that actual statement and this bounded interpretation. It must not fabricate an exact magic command or a reusable bearer capability.

This approval does not authorize research/backtest execution, data mutation, production strategy/config changes, KBase/Registry/Snapshot/Handoff/Memory content writes, Holdout access, Windows scheduler/ACL mutation, process cancellation, real Campaign execution, or production promotion.

## Supersession

`V3.4.1-P0R1` status becomes `SUPERSEDED_BY_V3.4.2_P0R2` for future control decisions. Existing files are not edited or deleted. P0R1 remains auditable history only.

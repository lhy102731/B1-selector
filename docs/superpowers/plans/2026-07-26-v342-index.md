## Purpose

This plan replaces `V3.4.1-P0R1`. It builds an auditable, fail-closed research control plane around the existing A-share research system without changing production strategy logic, signal rules, model parameters, validation scope, data bytes, or the daily production scheduler.

The target system can run multiple research cycles, commit only independently verified and scoped learning, feed safe learning into the next cycle, recover idempotently after a crash, and keep Final Holdout behind a separately authorized one-time boundary.

P0R1 remains immutable evidence. Its claimed authorization, task reports, initial inventory, and provisional entry policy cannot authorize or satisfy a V3.4.2 gate.

Natural-language authorization is recorded verbatim in a receipt; the system must not pretend that the exact historical magic command was sent.

## Non-negotiable architecture

1. Authority facts live only in `research_state/control_plane/authority/authority.sqlite3`.
2. Operational events live only in `research_state/control_plane/operational/operational.sqlite3`.
3. The stores share a small SQLite transaction implementation but never a file, schema owner, connection, `ATTACH DATABASE`, or cross-store transaction.
4. Authority changes write an outbox entry in the same authority transaction. Operational mirroring is idempotent by `event_id`; pending outbox blocks phase close.
5. Public hashes identify content but never confer authority. Capabilities are random, one-time, digest-only at rest, and bound to actor, invocation, attempt, phase, plan, scope, and instruction policy.
6. Runner output is raw evidence. A strict adapter plus an independent EvidenceAdapter computes scientific validity; Runner booleans are non-authoritative.
7. Learning Packets are content-addressed and create-only. Ledger, Memory, coverage, budget, and status are rebuildable projections of events.
8. New Campaign work items live in the OperationalJournal. Legacy TaskQueue, STOP files, status files, autorun loops, and AutonomousRunner state are adapters, never a second authority.
9. `run_research.py` owns the research/control-plane command registry. `run_research_cycle.py` may only translate legacy arguments or explain migration.
10. Final Holdout is consumed before access, exactly once, after candidate freeze, under a separate authorization. Its output never re-enters iterative memory.
11. Every phase follows `implementation -> code freeze -> final inventory -> independent entry-policy review -> immutable policy -> generic gate verify/close`.
12. P0's authority/bootstrap/gate trusted computing base is sealed after P0 PASS. A later modification requires a new P0 change request and attempt.

## Reuse and complexity budget

Reuse the existing KBase atomic publication logic, `lineage.py`, raw/indicator/signal cache formats, isolated workspaces, `git apply --check`, SQLite, `hashlib`, `jsonschema`, Pydantic, Tenacity, psutil, and model-aware tokenizers. Historical identity algorithms receive explicit legacy adapters; old IDs are not rewritten.

Do not add DVC, MLflow authority, Prefect, Temporal, Celery/RQ, another task queue, another usage ledger, a generic FSM, SQLAlchemy/Alembic, a second CLI owner, or a third authoritative database. A new durable artifact must declare its owner, schema, retention, recovery/rebuild behavior, and deletion safety.

## Cross-phase scientific invariants

- Rolling forward validation is the default for multi-year claims. Train/validation choose variants; each fold test is unseen and opened once.
- Purge and embargo are mandatory when labels, holding periods, or feature windows overlap.
- Reports identify exact code, runner, data generation, feature set, model artifact, thresholds, folds, label, horizon, and whether test years were unseen.
- Positive, negative, anti-factor, failed-usage, and PARTIAL results are retained with evidence and scope. A failed usage does not globally reject a mechanism.
- `NO_MATERIAL_FINDING` records a round outcome and information gain; it never creates an empty scientific claim.
- Final Holdout cannot choose, revise, or promote candidates and cannot enter the next-cycle context.

## Execution discipline

Each behavior is delivered as a vertical TDD slice: one public behavior test fails for the expected reason, the minimum implementation makes it pass, then a small refactor may occur while green. Targeted tests run first; the full repository test suite runs at the phase integration boundary. Control-plane-only changes do not justify a backtest.

Every completed and verified small stage receives its own Git commit. Exact files are staged; broad staging, reset, checkout-based cleanup, force operations, and commits of unrelated user changes are forbidden.

Phase gates remain serial. Independent implementation lanes may run concurrently only when file ownership does not overlap. External model suggestions are proposals; the primary controller reviews every line and owns all tests and commits.

## Rollout boundary

P0-P8 implementation PASS does not authorize a real Campaign. Rollout is separately gated:

1. C0: offline fake-provider, fake-clock, fake-PID chaos simulation for at least 20 cycles.
2. C1: separately authorized real-LLM dry run; no scientific Learning Commit.
3. C2: separately authorized two-cycle canary; no Final Holdout.
4. C3: only after canary audit may the operator authorize bounded hours/cycles/budget.

Production promotion remains manual. No gate auto-advances to the next phase.
